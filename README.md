# Requirement Analysis Skill / 对话式需求挖掘

从一个大概的业务场景出发，通过逐轮追问找到真实问题与具体卡点，整理成可供本人复述、讲师或业务方评审的需求描述。

保留角色、场景、动作、期望四维分析与 As-is/To-be 对照。四维是检查覆盖情况的工具，追问顺序随具体回答调整。

## 使用方法

将本目录交给支持 Skill 的 Agent，按所在工具的安装方式加载。安装位置、加载机制与实际调用以当前宿主为准；文件存在不等于已被调用。检查 Agent 是否读取了 `SKILL.md`，并用下面的开场实际走一轮对话。

### 课堂开场

把下面这段话和自己的场景一起发给 Agent：

> 请调用 requirement-analysis，进入课堂需求评审准备模式。我会先描述一个大概的场景，请每次只问一个关键问题，帮我找到真正要解决的问题，以及流程里具体卡在哪里。先不设计系统。整理好后，输出一页需求描述和一段 60—90 秒的口述稿，供我交给讲师评审。我的场景是：……

通常从最近一次实际任务开始：

> 用户：我是做培训的，想做个自动写招生文案的智能体。
>
> Agent：你想改善招生文案这项工作，智能体是目前想到的做法。最近一次准备招生文案时，具体发生了什么，让你觉得需要这个工具？
>
> 用户：反复改了很多次，最后还是没发。
>
> Agent：目前明确的是文案经历了多次修改，却没进入发布。最后一次决定不发时，具体是哪一点没解决？

以上为教学示例，不预设问题一定出在文案生成，也不把用户的第一种解释直接当作根因。

### 评审后继续

> 这是讲师给我的评审意见：……。请对照原需求区分新增事实、判断和待验证建议，修订同一份需求描述，说明这次改了什么、还缺什么。不要直接开始实现。

评审后，用户明确进入实现时，再基于修订范围推进最小方案。

### 批量需求

上传材料或列出多个场景时，先按目标与实际流程识别独立需求，确认优先项再逐个挖掘。不会仅因字数较多就拆成多个需求。同一场景的功能列表先视为线索。

多人评审按人员与需求编号分开整理，不混用彼此的事实。汇总表保留问题、卡点、依据/未知、优先级理由、评审状态和下一步。

## 工作流程

大概场景 → 最近一次真实工作 → 现状流程 → 问题与影响 → 具体卡点及依据 → 期望变化 → 本人核对 → 标准需求描述 → 人工评审 → 修订与下一步。

- 每轮最多一个核心问题；已知信息跳过，信息矛盾优先核对。
- 区分目标、问题、卡点与原因假设，不为凑深度无限追问。
- 用户要求先出稿或课堂时间到时，按现有信息收束并标注缺口。
- “本人核对”“讲师评审”“根因验证”“实际效果”是不同状态。
- 不把低频、能暂时忍受、无法量化等同于伪需求。
- 不强制生成量化指标；由使用者与反馈逐步澄清结果判断标准。

## 输出

一页需求描述包括：一句话需求、As-is/To-be、问题及影响、卡点位置、已有依据、原因假设与未知、本次优先范围、结果判断方法、下一步验证和请评审者重点判断的疑点。

课堂模式另附 60—90 秒口述稿。模板和完整行为规则以 [SKILL.md](SKILL.md) 为准，默认在对话里交付，只有用户要求保存时才创建文件。
